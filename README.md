# Jewel Tracker

أنت فريق تطوير كامل يعمل كـ Senior Product Architect + Full-Stack Engineer + UX Designer + Database Architect + DevOps Engineer + Security Engineer.

أريد منك بناء نظام ويب كامل من الصفر لإدارة مخزون ومبيعات ومتابعة طلبات داخلية لمجموعة محلات ذهب ومجوهرات لديها 5 فروع.

مهم جدًا:

هذا ليس نظام inventory عادي. هذا نظام عملي ومخصص لمتاجر الذهب والمجوهرات، حيث القطع متشابهة جدًا بصريًا، لذلك يجب أن يكون البحث بالباركود والصورة والصفات هو الأساس. النظام يجب أن يستبدل الاعتماد على الواتساب في سؤال "أين القطعة؟" و"كم وزنها؟" و"هل عندكم نفس الشكل؟".

الهدف التجاري:

- معرفة مكان كل قطعة فورًا

- البحث عن القطعة بالباركود أو الاسم أو الصورة أو المواصفات

- تسجيل الوزن والقيراط والمقاس والصور والسعر والفرع

- تسجيل طلبات العملاء وملاحظاتهم داخل النظام

- معرفة من سأل عن قطعة معينة ومتى وبأي سعر

- نقل القطع بين الفروع بشكل منظم

- منع الفوضى والتأخير والبحث اليدوي في الواتساب

البيئة الحالية:

- كل قطعة لديها Barcode من نظام POS موجود أصلًا

- أريد Web App مستقل أو متصل بالنظام الحالي

- يجب أن يكون النظام قابل للتعديل بسهولة في المستقبل

- يجب أن يكون مناسبًا لموظفين غير تقنيين

- يجب أن يعمل على الجوال والكمبيوتر بكفاءة عالية

- يجب أن يدعم العربية والإنجليزية من البداية

المتطلبات الأساسية للنظام

1) إدارة المنتجات

كل قطعة يجب أن تكون لها بطاقة مستقلة تحتوي على:

- Barcode فريد

- اسم المنتج

- فئة المنتج

- النوع: خاتم، سوار، سلسلة، حلق، طقم، ألماس، إلخ

- القيراط: 18K، 21K، ألماس، أو غيره

- الوزن

- المقاس إذا كانت خاتمًا

- عدد الصور مع رفع صور متعددة

- وصف مختصر

- الفرع الحالي

- الحالة: متوفر، محجوز، مبيع، تحويل، تالف، مفقود

- سعر التكلفة

- سعر البيع

- سعر العرض المؤقت إن وجد

- ملاحظات داخلية

- تاريخ الإضافة

- آخر تعديل

- من أضافه ومن عدله

2) البحث الذكي والسريع

يجب أن يستطيع الموظف البحث بواسطة:

- Barcode

- اسم المنتج

- جزء من الاسم

- القيراط

- الوزن

- المقاس

- الفرع

- الحالة

- الفئة

- صورة العميل أو صورة من النظام

البحث يجب أن يكون سريعًا جدًا، والواجهة يجب أن تظهر النتائج بأقل عدد نقرات ممكن.

3) طلبات العملاء

عندما يسأل عميل عن قطعة، يجب أن يستطيع الموظف إنشاء Request يحتوي على:

- اسم العميل أو رقم التواصل إن وجد

- الصورة المرسلة من العميل

- الوصف

- الميزانية

- المقاس المطلوب

- القيراط المطلوب

- الفرع المرتبط

- الموظف الذي سجله

- الحالة: Pending / Found / Quoted / Shown / Sold / Lost

- السعر الذي تم عرضه

- ملاحظات داخلية

- التاريخ والوقت

- إمكانية إضافة متابعة لاحقة

جميع الفروع يجب أن ترى هذه الطلبات فورًا، مع سجل كامل للتعديل.

4) التحويل بين الفروع

النظام يجب أن يدير Transfer Workflow واضح:

- طلب تحويل

- موافقة

- إرسال

- استلام

- إغلاق العملية

ويجب أن يحتوي التحويل على:

- Barcode القطعة

- من أي فرع

- إلى أي فرع

- من طلب التحويل

- من وافق

- تاريخ الإرسال

- تاريخ الاستلام

- الحالة

- ملاحظات

5) الصلاحيات والأدوار

دعم الأدوار التالية:

- Admin

- Manager

- Employee

الصلاحيات يجب أن تتحكم في:

- إضافة وتعديل المنتجات

- تعديل الأسعار

- الحذف

- اعتماد التحويلات

- بيع المنتج

- رؤية جميع الطلبات

- إدارة المستخدمين

- رؤية سجل العمليات

- تعديل الإعدادات العامة

6) سجل العمليات

كل عملية مهمة يجب أن تُسجل:

- إضافة منتج

- تعديل منتج

- تعديل سعر

- إنشاء طلب

- إضافة صورة

- إنشاء تحويل

- اعتماد تحويل

- استلام تحويل

- بيع منتج

- حجز منتج

- إلغاء حجز

- حذف منتج

- تغيير حالة

7) الواجهة وتجربة الاستخدام

يجب أن يكون النظام:

- Mobile-first

- سريع جدًا

- نظيف وبسيط

- مناسب لموظفين مبيعات

- مناسب للمديرين

- قليل النقرات

- لا يعتمد على تعقيد زائد

- قابل للاستخدام من الهاتف داخل المحل

8) قابلية التوسع والتعديل

أريد بنية قابلة للتطوير لاحقًا بدون كسر النظام.

لذلك:

- لا تكتب كل شيء بشكل hardcoded

- اجعل الفئات والحالات والفروع والأدوار قابلة للإدارة من قاعدة البيانات أو الإعدادات

- استخدم مكونات قابلة لإعادة الاستخدام

- افصل المنطق التجاري عن الواجهة

- اكتب كودًا نظيفًا وواضحًا وسهل الصيانة

- صمّم قاعدة البيانات بحيث يمكن إضافة حقول جديدة لاحقًا بدون فوضى

9) التكامل مع POS

إذا كان ممكنًا، ضع خطة أو نقطة تكامل مع POS الحالي عبر:

- API

- Import/Export

- Sync دوري

- أو أي طريقة عملية

لكن لا تفترض أن POS الحالي سيُستبدل بالكامل.

التقنية المطلوبة

ابنِ النظام باستخدام Stack حديث وعملي، ويفضل:

- Frontend: Next.js + TypeScript

- Backend: Next.js API Routes أو NestJS أو Laravel إذا كان أفضل

- Database: PostgreSQL

- ORM: Prisma إذا كان مناسبًا

- Auth: JWT أو session-based مع صلاحيات دقيقة

- UI: TailwindCSS + shadcn/ui أو ما يعادلها

- Storage للصور: سحابي

- Deploy: Docker + .env + إعدادات تشغيل واضحة

إذا كنت ترى Stack أفضل، اذكر السبب بوضوح، لكن أعطني في النهاية تنفيذًا عمليًا وليس نقاشًا نظريًا.

قيود صارمة

- لا تبنِ النظام كنظام inventory عادي لمستودع عام

- لا تعتمد على واتساب كجزء من الحل

- لا تجعل الواجهة معقدة

- لا تجعل البحث يدويًا فقط

- لا تجعل barcode مجرد حقل إضافي، بل اجعله مفتاحًا أساسيًا للبحث

- لا تكتب إجابة عامة سطحية

- لا تكتفِ بالتصميم، أعطني شيئًا يمكن تشغيله وتطويره

- لا توقف عند الخطة، أنشئ النظام فعليًا أو ابدأ ببناء نسخة MVP كاملة قابلة للتشغيل
